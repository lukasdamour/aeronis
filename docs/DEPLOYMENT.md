## Docker Compose setup

`docker-compose.yml` defines two services:

- **`app`** -- the Flask app (`server.py`) behind gunicorn, built from the root `Dockerfile`. Exposed on host port `8000`, mapped to container port `5000`.
- **`tiles`** -- the offline tile server (`tiles-pipeline/serve_tiles.py`), built from `tiles-pipeline/Dockerfile`. Exposed on host port `8765`, reading a `.mbtiles` file mounted read-only from `./tiles-pipeline/data/`.

```bash
make build   # docker compose build
make up      # docker compose up -d
make logs    # docker compose logs -f
make down    # docker compose down
make restart # docker compose restart
make shell   # shell into the app container
```

Once up, the app is at `http://localhost:8000` -- note the port mapping: the container listens on `5000` internally, but that's not exposed directly on the host, only `8000` is.

## Diagnosing a Docker deployment

If `make build` succeeds but the page doesn't load in the browser, check the container actually stayed up:

```bash
docker compose ps
docker compose logs app
```

A build succeeding only means the declared dependencies installed correctly -- it does not execute the app code. A container that starts and then immediately exits (visible as `Exited` in `docker compose ps`, with a traceback in `docker compose logs app`) usually means an import failed at startup -- for example, a Python dependency used by the code but missing from the Dockerfile's install list. If that happens after adding a new import somewhere in `core/`, check it's included both in `pyproject.toml`'s `dependencies` and in the `pip install` line in `Dockerfile`; the Dockerfile installs an explicit package list rather than `pip install .`, so the two can drift out of sync.

## Offline map tiles

The offline tile server (`tiles-pipeline/serve_tiles.py`) reads a single `.mbtiles` file -- a SQLite database of pre-rendered tiles -- and serves it over HTTP in a format MapLibre GL JS understands. It uses only the Python standard library (`sqlite3`, `http.server`), so the `tiles` container has no extra dependencies to install.

**You need to provide the `.mbtiles` file yourself.** It isn't generated by anything in this repository -- `docker-compose.yml`'s comment referencing a `build_offline_map.sh` script describes a step that hasn't been checked into the repo yet. Common ways to produce one for an area you want to fly offline in:

- Export one from [MapTiler](https://www.maptiler.com/) or [Maputnik](https://maputnik.github.io/) for your region.
- Generate one from raw OpenStreetMap data with a tool such as [`tilemaker`](https://github.com/systemed/tilemaker) or [`planetiler`](https://github.com/onthegomap/planetiler).

Once you have a file, drop it in `tiles-pipeline/data/` and point `TILES_FILE` at it (matching the filename in `docker-compose.yml`, which currently defaults to `spain.mbtiles`).

`tiles-pipeline/download_tiles.py` is a separate, simpler utility: it downloads raw OSM raster PNG tiles for a bounding box into `web/tiles/osm/`. It's independent from the `.mbtiles`/`serve_tiles.py` pipeline above -- the two aren't interchangeable -- and is mainly useful if you want a quick raster tile cache rather than setting up the vector tile server.

Without a `.mbtiles` file mounted, the `tiles` container starts but the tile server fails to bind cleanly to a missing source and offline tiles are simply unavailable for that session; the app itself still works and falls back to public OpenStreetMap tile servers as long as there's an internet connection.

## Giving the app access to Ollama

The AI assistant needs to reach a running [Ollama](https://ollama.com) instance. Inside the `app` container, `127.0.0.1` refers to the container itself, not your host machine -- so if Ollama runs on the host (the common case), you need to point the container at the host explicitly.

**1. In `docker-compose.yml`**, add to the `app` service:

```yaml
    environment:
      - HOST=0.0.0.0
      - PORT=5000
      - PYTHONUNBUFFERED=1
      - OLLAMA_HOST=http://host.docker.internal:11434
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

`extra_hosts` with `host-gateway` is required on Linux for `host.docker.internal` to resolve; on Docker Desktop (macOS/Windows) it already resolves natively, but leaving the entry in doesn't cause any harm there.

**2. On the host**, Ollama must accept connections from outside `localhost` -- by default it only binds to `127.0.0.1`:

```bash
OLLAMA_HOST=0.0.0.0:11434 ollama serve
```

Or, if Ollama runs as a systemd service, add `Environment="OLLAMA_HOST=0.0.0.0:11434"` to its unit file, then `systemctl daemon-reload && systemctl restart ollama`.

**3. Rebuild and restart:**

```bash
make down
make up
```

Verify from inside the container:

```bash
docker compose exec app curl http://host.docker.internal:11434/api/tags
```

A JSON list of installed models confirms it's working; the app's `/api/llm/config` endpoint (and the assistant panel's status line) will then report the assistant as available.

**Simpler alternative (Linux only, less isolated):** set the `app` service to `network_mode: "host"` instead of the above. It shares the host's network directly, so `127.0.0.1:11434` just works with no other changes -- but you lose the explicit `8000:5000` port mapping (the app listens directly on host port `5000`) and the container's network isolation.

## Desktop build

`desktop.py` runs the same Flask app (`server.py`) in a background thread of a PySide6 process, then opens a `QWebEngineView` pointed at it -- no separate server process, no Docker.

```bash
pip install -e . PySide6 --break-system-packages
python desktop.py
```

It also starts the offline tile server in a background thread if a `.mbtiles` file is present at `tiles-pipeline/data/spain.mbtiles`, using the same `serve_tiles.run_tile_server()` function the Docker `tiles` service uses. Ollama, if you want the AI assistant available, still needs to be running separately on the host -- since this isn't containerized, `OLLAMA_HOST`'s default of `127.0.0.1:11434` works without any of the Docker networking steps above.

Packaging as a standalone executable (PyInstaller or similar) is possible but not currently set up in this repository; `server.py` and `desktop.py` already handle the `sys.frozen`/`sys._MEIPASS` cases a PyInstaller build would introduce, for whenever that's added. An earlier Tauri-based packaging approach was tried and abandoned due to `file://` origin issues with the frontend; the `WEB_DIR` environment variable in `server.py` is a remnant of that approach.
